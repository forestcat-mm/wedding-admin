# 受付機能 v2 仕様 — wedding-admin

`00_spec/reception.md`（v1）への追加変更。v1の仕様・セキュリティ要件（ゲストAPIにメール等を含めない、トークン毎回再照会など）はすべて維持する。

## 前提
- SupabaseでSQL適用済み：`reception_tokens.default_side text not null default 'all'`（'groom' | 'bride' | 'all'）
- **実装前に既存スキーマを確認し、次の3点を判定する列を特定して報告すること。見つからない・曖昧な場合は実装に進まず質問する。**
  1. 新郎側 / 新婦側（guests のサイド列）
  2. 配席済み（卓・席の割り当て）
  3. 出席予定（欠席・削除済み（soft-delete）でない）

## 1. 表示対象を「配席済みの出席予定ゲスト」に限定
- `GET /api/reception/guests` はサーバー側で「出席予定 かつ 配席済み」のゲストだけを返す（クライアント側の絞り込みにしない）
- 各ゲストに `side`（'groom' | 'bride'）を含めて返す
- フィルタ「すべて / 未受付 / お渡し物あり」とカウンター「受付済 x / y」は、この対象集合を母数とする
- 管理画面のダッシュボードにある受付カード2枚も、同じ母数に揃える

## 2. サイド切替
- ヘッダーの「操作者: xxxx」の横に切替を置く：`新郎側 / 新婦側 / すべて`（セグメントボタン）
- 初期値の決め方
  - トークンでアクセス：トークンの `default_side`
  - 管理者ログインでアクセス：`all`
  - 端末で切り替えた値は localStorage に保存し、次回以降はそれを優先する（try/catchで囲み、失敗時は初期値を使う）
- `GET /api/reception/me` の返り値に `default_side` を追加する（管理者の場合は 'all'）
- 一覧・フィルタ・カウンターは選択中のサイドで絞り込む
- 検索時は、選択中サイドの結果を先に表示する。その下に「もう一方のサイド」の該当者を、サイドバッジ付き・薄い見た目で表示する（別サイドのゲストが来た場合でも受付できるようにするため）
- 各ゲストカード・行に小さなサイドバッジ（新郎側 / 新婦側）を表示する

## 3. 管理画面：トークン発行時の既定サイド
- 「受付トークン」タブの発行フォームに「既定サイド」（新郎側 / 新婦側 / すべて、初期値すべて）を追加する
- 一覧に既定サイドの列を追加し、発行後も変更できるようにする

## 4. PCレイアウト
既存のスマホレイアウトは維持し、画面幅に応じて切り替える。

- **1024px以上（PC）**
  - 上部固定のヘッダー：検索欄（幅広）、フィルタ、サイド切替、操作者、カウンター
  - 本体は表形式：受付ID｜氏名（漢字＋ローマ字）｜サイド｜卓・席｜お渡し物（各項目にお渡し済トグル）｜受付状態（受付済ボタン・時刻）
  - 行の高さは詰めすぎない（誤クリック防止）。未渡しのお渡し物がある行は左端に色帯を付ける
  - 表のヘッダーはスクロールしても固定する。表は横はみ出し時のみ横スクロールする
- **768〜1023px（タブレット）**：カードを2列で表示する
- **767px以下（スマホ）**：現状どおり1列のカード表示
- キーボード操作（PC）
  - ページを開いたら検索欄にフォーカスする
  - Escで検索をクリアする
  - 5桁を入力して1件だけ一致したら、その行をハイライトしてスクロールで表示する。Enterで受付済にする。お渡し物が未渡しなら、v1と同じ確認ダイアログを出す
- 確認ダイアログ・通信状態（未送信・再送中）の表示はPCでも同じ挙動にする

## 完了条件
- 欠席・未配席・削除済みのゲストが受付画面とAPIレスポンスに出ない
- トークンの既定サイドが初回表示に反映され、端末で切り替えた値が再読込後も保持される
- 別サイドのゲストも検索で見つかり、受付できる
- 1280px・820px・390px の各幅でレイアウト崩れがない（スクショで確認）
- v1の単体テストがすべて通り、上記についてのテストを追加する

## 実装メモ（2026-09-25、wedding-admin）

前提の「判定に使う列」は次のとおり確定した（schema.sql 参照）。

| 判定 | 列・条件 |
|---|---|
| 1. 新郎側 / 新婦側 | `guests.side`（'groom' / 'bride' / null）。null のときは紐付いた回答の `replies_admin.side` を使う |
| 2. 配席済み | `seating_assignments` に行がある。本人の `reply_people`（idx=0）を `person_type='reply_person'` で、未回答の仮配席は `person_type='guest'` で引く |
| 3. 出席予定 | `guests.deleted_at is null` かつ、招待者に紐付いた有効な回答（`replies_admin.matched_guest_id = guests.id`、`deleted_at is null`、`superseded_by is null`）の `attending = true` |

未回答のまま仮配席された招待者は「出席予定」に当たらないため対象に含めない（回答が届けば自動で対象になる）。

- API：`GET /api/reception/guests` はサーバー側で上記 3 条件で絞り、各ゲストに `side` を付ける。`GET /api/reception/me` は `default_side` を返す（管理者は 'all'）
- 受付画面：サイド切替（localStorage `rcpt_side`）、検索時は別サイドの該当者を下に薄く表示、1024px 以上は表、768〜1023px はカード 2 列、767px 以下は 1 列。検索欄に自動フォーカス、Esc でクリア、5 桁で 1 件一致なら強調して Enter で受付（確認ダイアログは v1 と同じ）
- 管理画面：トークン発行フォームと一覧に「既定サイド」。ダッシュボードの受付カードは同じ母数
- テスト：`npm test`（tests/worker.test.mjs）。v2 のケース（default_side、side、欠席・未配席・削除済み・未回答・仮配席の除外）を追加
